## 问题一：`超时原因：…` 回复被误判为「有歧义」

### 现象

- 消息：「超时原因：全部等木工统一上门维修」（ENGINEER 工程师A，13:30/13:31 两次发送）。
- 机器人回复：「⚠️ 这条消息有歧义，我无法确定你要做什么。涉及：维修、超时原因 请明确说明要执行的操作（如「报修」「完成」「取消」等）。」

### 生产实证（只读）

`semantic_decisions` 表两条记录（id 570、571）：

```
intent=system.clarify
fields={"clarification_reason": "同一消息包含多个业务动作，请拆分后重发"}
evidence=["维修", "超时原因"]
```

### 根因

`semantics/classifier.py` 在调用模型**之前**有一个本地「多动作守卫」（classifier.py:272-289）：

1. `_find_business_action_cues("超时原因：全部等木工统一上门维修")` 用子串匹配 `_BUSINESS_ACTION_CUES`，同时命中：
   - 「维修」→ `ticket.repair_plan.submit`（cue 列表含裸词「维修」）
   - 「超时原因」→ `ticket.timeout_reason.submit`
2. `len(action_cues) > 1` → 直接返回 `system.clarify`，**模型根本没被调用**。

用户是照系统提醒（「如未完成，请回复 #超时原因 说明情况」）格式答复的；「等木工统一上门维修」里的「维修」是理由文本，不是第二个业务动作。守卫把理由 payload 里的 cue 词误当成独立动作。

### 可选修复

| 选项 | 做法 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A（建议）** | `classify()` 里加「前导回复关键词优先」：消息以 超时原因/未完成原因/特殊情况/维修方式/维修方案/故障判断 开头（可带 `#`，后接冒号/空格）时，只保留该关键词对应意图的 cue，其余 cue 不参与多动作计数 | 最小侵入；只影响「回复格式」类消息；真正的多动作消息（如「先报修，修好之后就直接完毕」）仍走 clarify | 需再确认前导关键词清单与匹配边界（负例如「特殊情况怎么填」不可误匹配） |
| B | 削窄 repair_plan cue：裸「维修」不作为独立 cue（只留 维修方式/维修方案/采购/更换） | 从源头减少误判 | 会影响 2026-08-26 用户决策（cue 清单曾特意加入「维修」）；可能在别处引入回归 |
| C | 纯调提示词，让模型自己判 | 不动本地守卫 | 本地守卫在模型前短路，提示词救不了这种消息；需同时改守卫 |

### 建议

采用 **选项 A**，并补 TDD 测试：
- 「超时原因：全部等木工统一上门维修」→ 意图 `ticket.timeout_reason.submit`（模型真正被调用）；
- 「特殊情况：等待上门维修师傅…」→ `ticket.special_case.submit`；
- 回归：「先报修，修好之后就直接完毕」仍 → clarify（多动作守卫不被绕过）；
- 负例：「特殊情况怎么填」不应命中前导关键词。

## 问题二：待商榷工单成为路由盲区 → 误报「当前没有可操作的活动工单」

### 现象

- 消息：「@工程师B 还没修好，亿兆说维修师傅受伤了，没有人干活，安排不了」（MANAGER 马树鹏，14:43）。
- 机器人回复：「当前没有可操作的活动工单，请先创建工单。」

### 生产实证（只读）

`semantic_decisions` 记录 id 572：

```
intent=ticket.special_case.submit   ← 模型判对了！
confidence=0.72
fields={"special_case_reason": "维修师傅受伤了，没有人干活，安排不了"}
target_ticket_no=None
```

该群（cid_demo_group_b==，北京商场14大悦城品牌B店）唯一工单 id=49：

```
ticket_no=北京商场14大悦城品牌B店-商场14大悦城-7天-001
status=PENDING_NEGOTIATION（待商榷，2026-08-28 起）
```

### 根因

`db.list_active_tickets()`（db.py:1194-1200）只返回 `status IN ('ACTIVE','ACTIVE_OVERDUE')`；`TicketRepository.snapshot_candidates()` 以此为候选源。待商榷工单不在其中 → 候选为空 → 路由 `RouteDecision.CLARIFY` 无候选 → `pipeline._create_clarify_pending()` 空 ids 分支 → 回「当前没有可操作的活动工单」。

即：**模型判对了意图，但路由层找不到工单**，于是给出误导性文案。

### 关联：一个已存在的同族缺口

2026-08-28 事故修复时已记录：「特殊情况协议允许 PENDING_CONFIRM 但路由不可达（待产品决策）」。即 PENDING_CONFIRM（待店长确认）工单同样不在活动候选里，特殊情况路由不到。本次 PENDING_NEGOTIATION 是同一类问题的新实例。

### 可选修复（含产品决策点）

| 选项 | 做法 | 需用户拍板的点 |
|---|---|---|
| **A（建议核心）** | 协议 `ticket.special_case.submit` 的 `allowed_ticket_states` 增加 `PENDING_NEGOTIATION`；pipeline 对 special_case 意图把本群待商榷工单并入候选（仅在无活动候选时兜底并入，避免破坏多候选路由） | 是否同意「待商榷工单可登记特殊情况」这个产品行为 |
| B | 顺带把 PENDING_CONFIRM 也纳入 special_case 候选，补齐 2026-08-28 遗留缺口 | 是否现在就要动「待产品决策」区域 |
| C | 不改路由，只改文案：候选为空但群内有非活动工单时，回复解释「工单 X 当前为待商榷状态」而非「请先创建工单」 | 是否接受「登记不了、只解释」的折中 |

### 语义提示（请一并确认）

特殊情况登记 = 暂停时效/响应 SLA 计时。**待商榷工单本身已无截止时间**（deadline 已清、完全暂停），所以「在待商榷工单上登记特殊情况」不会改变任何计时——它更像「记录一条状态说明」。这与正常情况下的「暂停计时」语义不完全相同，请确认这是否是想要的行为，还是仅需回复解释。

### 建议

- 首选 **A**：协议加状态 + 路由兜底，让「还没修好+原因」能在待商榷工单上被接住并回执「⏸️ 已登记特殊情况：…」；
- **B（PENDING_CONFIRM）单独确认**，不随本次一起动，避免擅自改变上次的「待产品决策」；
- 若对「待商榷工单登记特殊情况」的语义有顾虑，退而求其次选 **C**。

补 TDD 测试：
- 群内唯一工单为待商榷 + special_case 决策 → 登记成功、有回执、不再出现「没有可操作的活动工单」；
- 回归：2026-08-28 守卫（「007今日胶未干」指向 PENDING_CONFIRM → 不登记并解释）保持不变；
- 回归：活动工单单候选的正常特殊情况登记不受影响。
