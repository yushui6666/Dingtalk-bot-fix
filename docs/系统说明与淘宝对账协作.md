# 钉钉群报修工单系统 · 说明与淘宝对账协作

> 更新：2026-08-24 · 对齐当前代码（v4.1 正式版 + 2026-08-24 四项改进）。与实现冲突时以代码为准。

## 一、系统概览

系统监听门店钉钉群的报修消息，自动建档、推进、完成工单，并在群里回复。核心原则：**群内正常沟通即业务**，显式关键词与自然语言都能识别，模型不可用时关键词仍可完成核心操作。

### 技术栈
Python 3.14 / asyncio / SQLite(WAL) / `dws` CLI（钉钉连接器）/ OpenAI-compatible 云端模型（可选）

### 数据（`data/tickets.db`，20 张表）
`groups` `tickets` `messages` `processed_events`（幂等台账）`message_attachments`（图片附件）`diagnosis_versions` `repair_method_versions` `timeout_cycles` `notification_deliveries`（Outbox）`inbox_messages`（收件箱）`semantic_decisions`（语义审计）`message_ticket_links` `ticket_contexts` `pending_actions` `action_executions` `schema_migrations` `delivery_confirmations` `taobao_orders` `order_monitor` `responsibility_cycles`

## 二、业务流程（新流程）

```
店铺同事/店长在群里发报修（自然语言或 #报修）
        │
        ▼ 建工单（必填：主题/位置/问题描述/时效；缺失 → 提示补充，不默认）
工程师回复故障判断 → 记录
        │
        ▼ 提交维修方式 + 淘宝订单号（订单号人人可发，由 AI 识别）
  登记订单监控 + 订单↔门店写入共享表（v4.1 起不再自动延期，签收后开始计时）
        │
        ▼ （另一个 AI 每天拉淘宝状态回传共享表）
调度器读共享表 → 状态变化时群内通知一次：
   · 卖家已发货      → 提醒「已发货，留意收货」（含物流单号）
   · 已签收/交易成功 → 提醒「开始计时维修」，次日起新增每日一催直至完成（2026-08-28：签收当天只发这一条，不重复催）
   · 交易关闭        → 提醒「订单因未付款已关闭，请处理」
        │
        ▼ 完成（2026-08-24 店长确认流）
店长发「修好了」/「#完毕」   → 直接完成
工程师发「修好了」/「#完毕」 → 工单转「待店长确认」，
    店长回「确认修好」→ 完成；回「没修好」→ 退回工程师继续处理

时效提醒（SLA）：到期前 6 小时群内提醒一次；超时再提醒一次并转「已超时」+ 开超时周期；
签收后未完成的工单自签收次日起每日催一次（签收当天已有「开始计时维修」通知）。责任方超 1h 未响应群内提醒一次，超 4h 升级（含单聊）各一次/周期，不循环。
```

### 关键动作与角色权限（对齐 `protocols/ticket_semantics.v4.json`）

| 动作 | 关键词/识别 | 允许角色 | 备注 |
|---|---|---|---|
| 报修建单 | `#报修` / 自然语言 | 店长、其他成员 | 必填：主题、位置、问题描述、时效（1天/3天/7天/待商榷） |
| 补充信息 | `#补充` / 自然语言 | 全员 | 静默处理，不回执 |
| 故障判断 | `#故障判断` / 自然语言 | 工程师 | 静默处理，不回执 |
| 维修方式 + 订单号 | `#维修方式` / 自然语言 | 店长、工程师、其他成员 | 订单号人人可发；登记监控、不延期 |
| 完成工单 | `#完毕` /「修好了」/ 自然语言 | 店长、工程师 | 店长发→直接完成；工程师发→转待店长确认 |
| 确认修好 | 「确认修好」等 / 自然语言 | 店长 | 仅限待确认工单；确认后工单完成 |
| 没修好 | 「没修好」等 / 自然语言 | 店长 | 仅限待确认工单；退回工程师继续处理 |
| 取消工单 | `#取消工单` / 自然语言 | 店长 | 高危动作需确认 |
| 重开工单 | `#重开工单` / 自然语言 | 工程师、店长、工程负责人 | 高危动作需确认 |
| 停止维修 | `#停止维修` / 自然语言 | 工程负责人 | 高危动作需确认；终态「已停修」 |
| 超时原因 | `#超时原因` / 自然语言 | 工程师 | 在超时周期内提交未完成原因 |
| 查询工单 | `#查询工单` | 全员 |  |
| 选择工单 | `#选择工单` | 全员 |  |

> 订单号提交：任何群成员都可以发订单号（由 AI 识别为维修方式提交），登记订单监控并写入共享表；
> v4.1 起**不再自动延期**——等货期间照常算时效，订单签收后才开始计维修时长。

## 三、淘宝对账协作（给另一个 AI）

### 共享表文件
```
/Users/example/Desktop/淘宝对账/订单门店状态表.xlsx
```
表头：`order_id | store | ticket_no | status | tracking_number | updated_at`

### 分工
| 写入方 | 写入内容 | 时机 |
|---|---|---|
| **报修系统（本系统）** | `order_id` `store` `ticket_no` 三列 | 群里提交订单号时追加一行 |
| **另一个 AI** | `status` `tracking_number` `updated_at` | 每天拉淘宝订单状态后回传更新 |

### 状态值（另一个 AI 回传，与 `scheduler.scan_order_status` 对齐）
| status 值 | 系统行为 |
|---|---|
| 含「发货」 | 群内提醒一次「订单已发货，留意收货」（含物流单号） |
| 含「关闭」 | 群内提醒一次「订单因未付款已关闭，请处理」 |
| 含「签收」或「交易成功」 | 提醒一次「已签收到货，开始计时维修」；每日一催自签收次日起直至完成（签收当天不催） |
| 其他（等待买家付款/已付款…） | 只记录状态，不通知 |

### 写入规范
- **幂等**：按 `order_id` 匹配，已存在则更新状态，不重复加行
- **读改写**：每次写入前先读最新文件，改完再写，避免覆盖对方更新
- 状态回传频率：每天一次即可（系统每 60s 扫一次表，检测到状态变化才通知）

> **写入失败兜底**（2026-08-25，本系统侧）：若提交订单时共享表正被 Excel/WPS
> 占用导致写失败，登记不受影响；未写入的订单在本地标记 `order_monitor.xlsx_synced=0`，
> 调度器每 5 分钟（`SHARED_TABLE_RESYNC_INTERVAL_SECONDS`）自动重试补写，
> 无需人工补行。对另一个 AI 无感知。

### 调度建议（给定时任务 AI）
另一个 AI 每天执行「拉淘宝订单状态 → 更新共享表」即可，无需懂本系统代码。示例 cron：

```bash
30 9 * * *  <另一个AI的淘宝状态拉取脚本>
```

本系统侧无需额外配置：只要 `python main.py` 在跑，调度器自动读共享表并通知。

## 四、运行方式

```bash
# 启动系统（PRODUCTION 模式，监听配置的群）
PATH="$HOME/.workbuddy/binaries/node/cli-connector-packages/bin:$PATH" \
  python main.py --mode PRODUCTION

# 运行模式：SHADOW（只记录不执行）/ ASSISTED（模型动作全确认）/ PRODUCTION
python main.py --mode SHADOW

# 手动导入淘宝对账地址表（快递确认增强用）
python -m reconciling.import_orders --xlsx "/Users/example/Desktop/淘宝对账/订单地址明细.xlsx"

# 完整流程模拟（假分类器，可重复演示）
python scripts/simulate_flow.py

# 测试
python -m pytest tests/ -q
```

### 环境变量
- **`.env` 自动加载**：启动时 `config._load_dotenv()` 读取项目根目录 `.env`（无第三方依赖）；只填充进程中不存在的键，真实环境变量优先。改升级对象等配置只需编辑 `.env` 后重启
- `TAOBAO_ORDER_DETAIL_XLSX` / `TAOBAO_PENDING_XLSX`：对账导入源文件路径
- `ORDER_STORE_TABLE_PATH`：订单↔门店共享表路径
- `SHARED_TABLE_RESYNC_INTERVAL_SECONDS`：共享表写失败后的补同步重试间隔（默认 300 秒）
- `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`：云端模型配置
- `SLA_REMIND_BEFORE_HOURS`：时效到期提醒提前量（代码固定 **6 小时**，非环境变量；响应 SLA 另有 `RESPONSE_SLA_ENABLED` 总开关（默认 true，`false` 时整条静默，不影响其他提醒）、`RESPONSE_SLA_FIRST_HOURS` / `RESPONSE_SLA_ESCALATE_HOURS` / `RESPONSE_SLA_EFFECTIVE_FROM` 可用环境变量覆盖，默认 1h 提醒 / 4h 升级）
