## 一、消息处理流程

### 1.1 总览

```
钉钉群消息
  │  dws event +listen-im 监听（每群一个进程，断线自动重连）
  ▼
标准化 + 角色识别（店长/工程师/其他成员/系统账号）
  │  系统账号（工程部AI）回流自动过滤
  ▼
收件箱入队 inbox_messages（幂等：同一条消息只入队一次）
  │
  ▼
Inbox Worker ── 跨群并行、群内按 (sent_at, message_id) 串行 ──
  │
  ├─ ① 待确认回复？  （确认/拒绝/修正 已有待办动作）
  ├─ ② 语义识别      关键词快路径（本地） 或  云端模型（受协议约束）
  ├─ ③ 语义决策审计   落库 semantic_decisions
  ├─ ④ 多工单路由     归属到具体工单
  ├─ ⑤ 校验          角色/必填字段/枚举/工单状态/版本
  ├─ ⑥ 待确认 or 执行 一个短事务（唯一执行记录 + 业务变更 + 归属 + 通知）
  └─ ⑦ 群通知        Outbox 异步发送
```

### 1.2 分阶段明细（按一条消息跟踪）

| 阶段 | 发生什么 | 可能结局 |
|---|---|---|
| **标准化** | NDJSON 事件 → 统一结构；缺字段/时间非法 → 丢弃 | 丢弃 / 进入收件箱 |
| **入箱** | `inbox_messages` 写入；message_id 重复 → 跳过 | RECEIVED |
| **待确认回复** | 该用户有 WAITING 待办时，识别「确认/拒绝/修正」 | 执行 / 取消 / 修正后执行 |
| **语义识别** | 云端模型判类（2026-08-20 起全面由 AI 判断，`#` 关键词语法仍可识别） | 模型决策 / 模型降级 |
| **模型降级** | 模型超时/失败 → 退避重试 `[2s,10s]`，3 次后死信 | RETRY_PENDING → DEAD_LETTER |
| **编号硬校验**（#1） | 显式编号在本群查不到 → **硬拒绝**并列候选；状态不允许 → 明确提示 | REJECTED（不静默归属） |
| **路由** | 编号 > 引用 > 用户30分钟上下文 > 语义top1 > 单候选（候选状态按协议 `allowed_ticket_states`：完成/取消/停修含 `PENDING_NEGOTIATION`；取消/停修含 `PENDING_CONFIRM`；确认类动作只取 `PENDING_CONFIRM`。2026-09-14 修复待商榷单不可达） | ROUTED / CLARIFY / CREATE |
| **校验** | 角色、必填字段、枚举、工单状态、乐观版本 | AUTO_EXECUTE / WAITING_CONFIRMATION / VALIDATION_REJECTED / IGNORE |
| **执行** | 一个事务：唯一执行记录 → CAS 业务变更 → 消息归属 → 幂等台账 → 通知 | OK / REJECTED(版本冲突) / INTERNAL_ERROR |
| **确认窗口归档**（#3） | 群内存在 PENDING_CONFIRM 工单时，所有成员消息强制归档进该工单 | CONFIRM_WINDOW 归属 |
| **收尾** | 收件箱置 COMPLETED；按静默化策略决定是否发声 | COMPLETED |

### 1.3 每种结局对群里的表现

> 静默化原则（2026-08-24 #2）：**只在需要某方作出操作或确认时发声**。

| 结局 | 群里看到 |
|---|---|
| 建单成功 | 一行式回执「✅ 已建单 编号｜主题｜时效｜截止」（启动工程师响应时钟，保留） |
| 其他操作成功 | **静默**（补充/故障判断/维修方式/超时原因/取消/停修/重开/选单/订单登记等） |
| 工程师报完工 | 「🔧 请店长回复「确认修好」…」（需店长确认，保留） |
| 校验拒绝 | 「⚠️ 未找到工单 + 本群候选短编号 + 近似建议」／缺少字段／无权限等明确提示 |
| 待确认 | 「确认执行：ticket.cancel（…）？回复「确认」继续」 |
| 多工单歧义 | 列出候选工单，请选择或提供编号 |
| 模型降级重试 | 群内无动作（后台重试） |
| 死信 | 「智能识别暂时不可用，本条消息未执行，请稍后重试或联系管理员」 |

## 二、工单生命周期

### 2.1 状态机

```
                 ┌──────────────────────────┐
                 │        ACTIVE            │ 处理中
                 │ （订单签收后计时维修）       │
                 └──────┬───────┬───────────┘
        ┌──── 报修建单 ──┘       │
        │                      ├── 超时效 → 【ACTIVE_OVERDUE】（调度器自动推进 + 建超时周期）
        ▼                      │
   【ACTIVE】                  ├── 工程师报完工 → 【PENDING_CONFIRM】⏳ 待店长确认
        │                      │      ├─ 店长「确认修好」→【COMPLETED】✅ 终态
        │                      │      └─ 店长「没修好」→ 退回【ACTIVE】
        │                      │      （店长本人报完工 → 直接【COMPLETED】）
        │                      │
        └── 取消（需确认）──────►【CANCELLED】取消（终态）
                                 │
                                 └── #重开工单 ──► 【ACTIVE】（reopen_count+1）
```

### 2.2 状态定义（当前实际）

| 状态 | 含义 | 是否终态 | 当前是否自动切换 |
|---|---|---|---|
| `ACTIVE` | 处理中 | 否 | ✅ 建单时进入；被「没修好」/重开退回 |
| `ACTIVE_OVERDUE` | 已超时 | 否 | ✅ 调度器扫描超时效工单自动推进（幂等），并建超时周期 |
| `PENDING_CONFIRM` | 待店长确认 | 否 | ✅ 工程师报完工时进入；责任方切店长侧，确认期聊天强制归档 |
| `COMPLETED` | 已完成 | 是 | ✅ 店长「确认修好」或店长本人 `#完毕` |
| `CANCELLED` | 已取消 | 是 | ✅ 取消确认后 |

### 2.3 各动作如何改变工单

| 动作 | 触发 | 工单变化 |
|---|---|---|
| 建单 | `#报修` / 自然语言 | 新建 ACTIVE；编号 `店名-主题-时效-序号`；时效必填（1天/3天/7天/待商榷），缺失 → 提示补充，**不默认** |
| 补充 | `#补充` / 自然语言 | 追加问题描述；版本 +1（**静默**） |
| 故障判断 | `#故障判断` / 自然语言 | 写入 diagnosis_versions（留版本历史，**静默**） |
| 维修方式 + 订单号 | `#维修方式` / 自然语言 | 写入 repair_method_versions + 登记监控/共享表（**静默**；v4.1 起不再自动延期，签收后计时） |
| 超时原因 | `#超时原因` | 写入 timeout_cycles 解释超时周期（**静默**） |
| 完成（工程师） | 「修好了」/`#完毕` | ACTIVE/ACTIVE_OVERDUE/**待商榷** → **PENDING_CONFIRM**（closed_at 留空；责任方切店长侧；群内请店长确认） |
| 完成（店长本人） | 「修好了」/`#完毕` | ACTIVE/ACTIVE_OVERDUE/**待商榷** → COMPLETED（直接完成） |
| 确认修好（店长） | `#确认修好` / 自然语言 | PENDING_CONFIRM → COMPLETED；留痕 `completed_confirm_by/at` |
| 没修好（店长） | `#没修好` / 自然语言 | PENDING_CONFIRM → ACTIVE，交还工程师并通知 |
| 取消 | `#取消工单` / 自然语言 | ACTIVE/ACTIVE_OVERDUE/PENDING_CONFIRM/**待商榷** → CANCELLED（**需确认**） |
| 停止维修（工程负责人） | `#停止维修` | ACTIVE/ACTIVE_OVERDUE/PENDING_CONFIRM/**待商榷** → STOPPED 终态，强制记录停修原因 |
| 重开 | `#重开工单` | COMPLETED/CANCELLED/STOPPED → ACTIVE（reopen_count +1，**需确认**） |
| 查询 | `#查询工单` | 只读，列活动工单（带编号可查终态工单） |
| 选择 | `#选择工单` | 建立该用户 30 分钟上下文，不改变工单；成功回执「✅ 已切换到工单 …」（2026-08-25 用户要求） |

### 2.4 工单关键字段

- **编号**：`店名-主题-时效-序号`（如 `测试群（示例）-博物馆-3天-001`），序号每群独立递增
- **`version`（乐观锁）**：每次业务变更 +1；并发冲突时 CAS 更新失败 → 拒绝并提示，不覆盖他人更新
- **截止时间**：创建时 = 建单时间 + 时效；订单签收后开始计维修时长（不再自动延期）
- **`waiting_side` / `waiting_since`**：当前等待责任方（工程师侧/店长侧）与起点，驱动响应 SLA 提醒/升级
- **`completed_confirm_by` / `completed_confirm_at`**：店长确认完成留痕
- **`reopen_count`**：重开次数；**`cancelled_at/by/reason`**、**`stopped_at/by/reason`**：取消/停修留痕
- 诊断/维修方式都有**版本历史**（`is_current=1` 标记当前值）

## 三、关键机制

### 3.1 多工单并行与路由

- **同群可同时存在多张活动工单**（v4 已删除"每群一张"限制）
- 消息归属按 **5 级优先级**：明确编号 > 钉钉引用 > 用户 30 分钟上下文（`#选择工单`）> 语义评分 top1（≥0.90 且分差≥0.15）> 单候选兜底
- **歧义不猜**：多候选且无信号 → 回群列出候选，让用户选或提供编号

### 3.2 待确认动作（高危防护）

取消/重开/模型高置信动作 → 建 WAITING 待确认 → 群内问「确认？」：
- 用户「确认」→ 再次校验工单版本未变 → 执行
- 用户「拒绝」→ 取消；30 分钟未回 → EXPIRED
- 同一 (群,用户) 至多一个待办，新动作自动覆盖旧的

### 3.3 订单监控（淘宝采购协作）

```
提交订单号 → 登记订单监控 + 写入共享表 订单门店状态表.xlsx（order_id/store/ticket_no）
         → 另一个 AI 每天回传 status/tracking
系统读共享表，状态变化时群内通知一次：
  · 卖家已发货 → 提醒「已发货，留意收货」
  · 已签收     → 开始计算维修时长，次日起新增每日提醒直至完成（签收前不占时效；2026-08-28 起签收当天只发「开始计时维修」一条，不重复催）
  · 交易关闭   → 提醒「订单因未付款已关闭」
```

> **写入兜底**（2026-08-25）：登记时先写本地库再写共享表；共享表被 Excel/WPS
> 占用等导致写失败时不阻断登记、不报错给群——订单保持 `xlsx_synced=0`，
> 调度器 `scan_shared_table_resync` 每 5 分钟重试补写直至成功。

> v4.1 起不再「提交订单号自动延期 +3 天」，改为**签收后开始计时**（用户决策 2026-08-14）。

### 3.4 SLA 提醒（两类）

**时效 SLA（维修时长）**
- 活动工单时效**前 6 小时**（`SLA_REMIND_BEFORE_HOURS=6`）→ 群提醒一次「时效即将到期」
- **已超时** → 自动推进 `ACTIVE_OVERDUE`（幂等）+ 建超时周期 + 群提醒一次
- 订单已签收仍在处理 → 自签收次日起每日一催直至完成（签收当天不催，2026-08-28）

**响应 SLA（责任方响应，2026-08-24 #4）**

复用 `waiting_side / waiting_since` 责任方机制，调度器扫描所有等待中工单：

| 阶段 | 动作 |
|---|---|
| 超 **1h** 未响应 | 群内提醒责任方（每个等待周期一次） |
| 超 **4h** 未响应 | 群内升级提醒责任方 + 升级对象，并对**升级对象单聊一次**（群内与单聊均每周期只发一次，不循环；用户决策 2026-08-26，`waiting_side` 变更即自然换挡去重） |

- 工程师侧升级对象：工程总监A（总工程师，userId 已核实：门店 CSV「总工程师userId」= `900000000000000001`，已写入 `.env` 并随 `config._load_dotenv()` 自动生效；未配置时回退群配置 `engineering_leader_id` 同值）。换人只改 `.env` 重启；店长侧不走 `.env`（用户决策 2026-08-25），仍按 CSV 导入的各群区域经理路由
- 店长侧升级对象：该群区域经理（含 `PENDING_CONFIRM` 的店长确认超时）。姓名↔ID 已按《门店群数据汇总_v2.csv》「区域负责人userId」核实并与 `groups.json` 比对一致：上海区 = 区域经理A `90000000000000004`（15 店）；杭州/北京/常州/苏州区 = 区域经理B `9000000000000002`（14 店）；两个测试群不在 CSV 内，leader 为建群时手动配置的 `9000000000000001`
- **存量豁免（一次性分界，用户决策 2026-08-26）**：`RESPONSE_SLA_EFFECTIVE_FROM = 2026-08-26 15:00:00` 之前建单的工单一律不参与响应 SLA（一级提醒/升级/单聊均不发），仅分界后新建工单纳入；时效 SLA 不受影响。分界值晚于全部存量单最后建单时间（14:43），存量工单自然完结后该条件恒空转；移除方式见 `config.py` 注释
- **总开关（2026-08-26）**：`RESPONSE_SLA_ENABLED`（`.env`，默认 `true`）为 `false` 时整条响应 SLA 静默（1h 提醒/4h 升级/单聊均不发），不影响时效 SLA、订单签收等其他提醒；改后重启生效

### 3.5 并发与幂等

- **跨群并行、群内串行**：某群慢模型不阻塞其他群；同群按顺序处理
- **事务型 Outbox**：业务变更与通知预写同事务，提交后异步发送
- **乐观版本**：所有写工单都带 `version` 条件，冲突即拒
- **幂等三层**：收件箱 message_id 主键 / 幂等台账 processed_events / 执行记录 action_executions
